# Аудит клиентского пути — оркестратор

> Русская версия `SKILL.md`. Справочники — `references/ru/`. Отвечай на языке пользователя.

Путь, собранный ИИ, обычно гладкий: каждый шаг удаётся, пользователь понимает всё с первого раза, внешние системы отвечают. Человек, который знает продукт, видит три типа расхождений — **логика**, **покрытие**, **нагрузка**. Каждый тип проверяет своё семейство методов в отдельном агенте: аудиторы не подстраиваются друг под друга и работают параллельно. Четвёртый агент сводит находки в решения.

```
                 ┌─ journey-cjm-auditor   (скилл journey-cjm)   ─┐
journey.json ──► ├─ journey-edge-auditor  (скилл journey-edge)  ─┤──► journey-verdict ──► verdict.md + specs/
  frame.md       └─ journey-load-auditor  (скилл journey-load)  ─┘     (скилл journey-verdict)
```

Оркестратор (ты) готовит вход, запускает агентов, проверяет их выход и показывает итог. Сам находки не пишешь: если влезешь в работу аудитора, пропадёт независимость.

## Шаг 0. Рамка и версия

1. Проверь версию входа: `git log -1 -- <файл>` или даты, есть ли копия новее в других ветках. В отчёт идёт дата коммита, а не время checkout.
2. Запиши `frame.md` (5–8 строк): одна главная персона (остальные списком), JTBD, триггер, сценарий, критерий успеха от пользователя, устройство и контекст, источник пути (ИИ / человек / код), список входов с путями.
3. Видение владельца. Если его нет, спроси 3–5 пунктов одним сообщением. Если спросить нельзя — восстанови из целевых разделов документа и запиши `origin` у каждого пункта.

| Вход | Что делать |
|---|---|
| Текст или таблица CJM (md, docx, Notion, Figma, скрин) | Нормализуй в JSON |
| Прототип или живой URL | Передай аудитору краевых сценариев для режима браузера |
| Код фронта | Пути к маршрутам, состояниям ошибок, текстам — в `frame.md` |
| Снимки, прогоны, аналитика | Пути в `frame.md`: аудиторы берут оттуда доказательства |

## Шаг 1. Нормализация

Переведи путь в `journey.json` по `references/ru/journey-format.md`: одно действие на шаг, отклик, эмоция с причиной, `src` и `evidence` раздельно, сбой и выход, `load`, ветки. Всё додуманное перечисли в `frame.md` → «Додумано при нормализации».

Найди скрипт один раз и проверь файл, прежде чем раздавать его агентам:

```bash
JC=$(find -L ~/.claude ~/.codex ~/.agents . -maxdepth 9 -path '*journey-audit/scripts/journey_check.py' 2>/dev/null | head -1)
python3 "$JC" check <work>/journey.json --lang ru
```

Если скрипт падает или выдаёт L00 (дубли id), исправь JSON. Аудиторы работают с одним файлом и его не меняют.

## Шаг 2. Три аудитора параллельно

Рабочая папка `<work>` — рядом с исходником или там, где сказал пользователь. Создай в ней `cjm/`, `edge/`, `load/`, `verdict/`.

Запусти три агента **в одном сообщении**. Если доступны типы `journey-cjm-auditor`, `journey-edge-auditor`, `journey-load-auditor` (плагин Claude Code или Codex с файлами `codex/agents/*.toml`, скопированными в `~/.codex/agents/`), используй их; иначе — субагента общего назначения (`default` / `worker` в Codex). В каждом промпте один и тот же блок параметров:

```
Brief: <папка этого скилла>/agents/<cjm|edge|load>-auditor.md
Script: <путь из $JC>
Work folder: <work>
Input: <work>/journey.json, <work>/frame.md
Source: <путь>
Mode: full | quick
Language: ru
Personas: yes (N) | no          ← только для edge
Browser: URL | no               ← только для edge
```

Каждый аудитор пишет `<family>/findings.json` (контракт — `references/ru/findings-contract.md`, отчёт — в поле `report_md`) и возвращает 3–5 строк.

Когда все трое вернулись, проверь контракт и разверни отчёты:

```bash
python3 "$JC" findings <work> --lang ru
python3 "$JC" render <work>
```

Если у аудитора ошибки контракта, отправь их ему обратно и не передавай его файл вердикту. Если аудитор вернул отчёт текстом (среда запретила файл), сохрани его в `<family>/report.md` сам.

**Субагентов в среде нет** (некоторые агенты кода): проведи трёх аудиторов по очереди сам, каждого с чистого листа — читай только его бриф и его скилл, не перечитывай находки прошлых семейств до вердикта.

## Шаг 3. Вердикт

Запусти `journey-verdict` (или агента общего назначения с `Brief: <папка этого скилла>/agents/verdict.md`) с той же папкой и скриптом. Он читает три `findings.json`, `journey.json`, `frame.md` и пишет `verdict/verdict.json` (markdown в поле `files`), `backlog.json`, `merged.json`. Затем `python3 "$JC" render <work>` — появятся:

- `verdict/verdict.md` — вердикт, приоритеты P0–P2, цели с метриками, TO BE, план проверки;
- `verdict/specs/G-NN.md` — спека на каждую цель P0 и P1.

## Шаг 4. Итог пользователю

Собери `journey-audit-<slug>.md` по `references/ru/report-format.md`: рамка, сводка с цифрами, вердикт, цели P0 со ссылками на спеки, ссылки на отчёты семейств. Ссылайся, а не пересказывай.

В чат: вердикт одной строкой, 3–5 целей P0/P1 с метрикой, пути к файлам, что не проверено.

## Режимы

| Запрос | Что запускать |
|---|---|
| Полный аудит (по умолчанию) | Шаги 0–4, все четыре агента |
| «Только логика» / «только краевые» / «только нагрузка» | Шаги 0–1 и один аудитор без вердикта — или скилл семейства напрямую: `journey-cjm`, `journey-edge`, `journey-load` |
| «Что чинить», находки уже есть | Только шаг 3 |
| Быстрый взгляд | `Mode: quick` — без персон и развёрнутых веток |

## Правила, которые держат аудит честным

- **Классы доказательности не смешиваются**: предоставлено, нет во входе, синтетическое поведение, интерпретация, гипотеза, неизвестно. Одна находка — один класс.
- **Не выдумывай экраны и переходы.** Неизвестное — `unknown`.
- **Полезное трение не режется**: подтверждение необратимого, согласие, медицинские, юридические и финансовые границы.
- **Провал ценности — не провал интерфейса.** Если сервис не решает задачу, кнопкой это не лечится.
- **Регистр**: факты, цифры, следствия, без оценочных слов.
- **Браузер**: формы читать можно, отправлять нельзя (кроме тестового контура с явного разрешения). Не платить, не регистрироваться на чужих сервисах, не вводить пароли.
- **Персональные данные** из входов в отчёты не переносить: ссылайся на id шагов и пересказывай.
