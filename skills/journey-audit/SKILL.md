# Journey audit — orchestrator

> Русская версия инструкций: `SKILL.ru.md`. Answer in the user's language.

A journey written by AI is usually smooth: every step succeeds, the user understands everything on the first try, external systems always answer. A person who knows the product sees three kinds of gaps — **logic**, **coverage**, **load**. Each kind is checked by its own family of methods in its own agent, so auditors do not anchor on each other and run in parallel. A fourth agent turns their findings into decisions.

```
                 ┌─ journey-cjm-auditor   (skill journey-cjm)   ─┐
journey.json ──► ├─ journey-edge-auditor  (skill journey-edge)  ─┤──► journey-verdict ──► verdict.md + specs/
  frame.md       └─ journey-load-auditor  (skill journey-load)  ─┘     (skill journey-verdict)
```

You (the orchestrator) prepare the input, launch the agents, validate their output and present the result. You do not write findings yourself: stepping into an auditor's work breaks its independence.

## Step 0. Frame and version

1. Check the input version: `git log -1 -- <file>` or file dates; look for a newer copy in other branches. Report the commit date, not the checkout time.
2. Write `frame.md` (5–8 lines): one main persona (others as a list), JTBD, trigger, scenario, success criterion from the user's side, device and context, source of the journey (AI / human / code), list of inputs with paths.
3. Owner's vision. If there is none, ask for 3–5 items in one message. If you cannot ask, reconstruct it from goal sections of the document and set `origin` on each item.

| Input | What to do |
|---|---|
| CJM as text or table (md, docx, Notion, Figma, screenshot) | Normalize to JSON |
| Prototype or live URL | Pass to the edge auditor for browser mode |
| Front-end code | Paths to routes, error states, copy — into `frame.md` |
| Screenshots, test runs, analytics | Paths into `frame.md`: auditors take evidence from there |

## Step 1. Normalize

Convert the journey to `journey.json` following `references/journey-format.md`: one action per step, response, emotion with a reason, `src` and `evidence` kept apart, failure and recovery, `load`, branches. List everything you had to invent in `frame.md` → "Invented during normalization".

Locate the script once and validate the file before handing it out:

```bash
JC=$(find ~/.claude ~/.codex ~/.agents . -path '*journey-audit/scripts/journey_check.py' 2>/dev/null | head -1)
python3 "$JC" check <work>/journey.json
```

If the script fails or reports L00 (duplicate ids), fix the JSON. Auditors share this file and never change it.

## Step 2. Three auditors in parallel

Work folder `<work>` — next to the source or where the user said. Create `cjm/`, `edge/`, `load/`, `verdict/` inside.

Launch the three agents **in one message**. Use agent types `journey-cjm-auditor`, `journey-edge-auditor`, `journey-load-auditor` when available (plugin install); otherwise a general-purpose agent. Every prompt carries the same parameter block:

```
Brief: <this skill dir>/agents/<cjm|edge|load>-auditor.md
Script: <path in $JC>
Work folder: <work>
Input: <work>/journey.json, <work>/frame.md
Source: <path>
Mode: full | quick
Language: en | ru
Personas: yes (N) | no          ← edge only
Browser: URL | no               ← edge only
```

Each auditor writes `<family>/findings.json` (contract: `references/findings-contract.md`, the report goes into the `report_md` field) and returns 3–5 lines.

When all three are back, validate and expand the reports:

```bash
python3 "$JC" findings <work>
python3 "$JC" render <work>
```

If an auditor has contract errors, send them back to that auditor and do not pass its file to the verdict. If an auditor returned its report as text (the environment blocked file creation), save it to `<family>/report.md` yourself.

**No subagents in your environment** (some coding agents): run the three auditors one after another yourself, each from a clean context — read only its brief and its family skill, and do not reread previous families' findings until the verdict.

## Step 3. Verdict

Launch `journey-verdict` (or a general-purpose agent with `Brief: <this skill dir>/agents/verdict.md`) with the same work folder and script. It reads the three `findings.json`, `journey.json`, `frame.md` and writes `verdict/verdict.json` (markdown in the `files` field), `backlog.json`, `merged.json`. Then run `python3 "$JC" render <work>` to get:

- `verdict/verdict.md` — verdict on the journey, priorities P0–P2, goals with metrics, TO BE, validation plan;
- `verdict/specs/G-NN.md` — a spec for every P0 and P1 goal.

## Step 4. Result for the user

Assemble `journey-audit-<slug>.md` following `references/report-format.md`: frame, summary with numbers, verdict, P0 goals with links to specs, links to family reports. Link instead of retelling.

In chat: the verdict in one line, 3–5 P0/P1 goals with their metric, file paths, what was not checked.

## Modes

| Request | Run |
|---|---|
| Full audit (default) | Steps 0–4, all four agents |
| "Only logic" / "only edge cases" / "only load" | Steps 0–1, one auditor, no verdict — or call the family skill directly: `journey-cjm`, `journey-edge`, `journey-load` |
| "What to fix", findings already exist | Step 3 only |
| Quick look | `Mode: quick` — no personas, no expanded branches |

## Rules that keep the audit honest

- **Evidence classes never mix**: provided, absent, synthetic, interpretation, hypothesis, unknown. One finding — one class.
- **Do not invent screens or transitions.** Unknown stays `unknown`.
- **Useful friction stays**: confirmation of irreversible actions, consent, medical, legal and financial safeguards.
- **A value failure is not a UI failure.** If the service does not solve the job, a button will not fix it.
- **Register**: facts, numbers, consequences; no evaluative adjectives.
- **Browser**: reading forms is fine, submitting is not (except a test environment with explicit permission). Never pay, sign up on third-party services or type passwords.
- **Privacy**: never copy personal data from inputs into reports; use step ids and paraphrase.
