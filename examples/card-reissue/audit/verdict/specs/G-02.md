# G-02 · P0 · A failed block says the card is NOT blocked and offers a way out

## Problem
If the provider does not confirm the block, the app shows a generic error. The card stays active and the user has no next step (b1.s1). The normal wait (s4) has a spinner with unknown duration.
Findings: CJM-07 (critical, provided), EDGE-01 (critical, provided), CJM-08 (medium, provided), LOAD-03 (high, low confidence: the 30 s wait comes from normalization).

## Goal and metric
- Failed block attempts resolved (blocked on retry or call started) within 10 min · now: not measured · target: ≥ 95 % · how: `card_block_failed` → `card_blocked` or `hotline_call_tapped`.
- Failures that show the "NOT blocked" state · target: 100 %.
- First task: log block duration to set the expected-time text and the timeout.

## Scope
- s4 wait → expected time and a timeout.
- b1.s1 → new failure state with retry and a 24/7 line (branch e1).
- s5 → plain-language confirmation (also closes P2 CJM-09, LOAD-06).
- Out of scope: blocking without the app (P2, EDGE-11).

## States
| State | What the user sees | What they can do |
|---|---|---|
| Loading | Progress text with expected time | Wait |
| Slow (over N s) | "Still working. Your card is not blocked until you see a confirmation." | Wait, call |
| Error / timeout | "Your card is NOT blocked yet" | Try again, call |
| Offline | "No connection. Your card is NOT blocked yet." | Retry on reconnect, call |
| Success | Plain confirmation | Continue |

## UI copy
- Progress: "Blocking card •• 1234…" / "Usually takes about N seconds."
- Error heading: "Your card is NOT blocked yet"
- Error text: "Try again or call us. The line works 24/7."
- Buttons: "Try again" · "Call 24/7 block line"
- Success: "Card •• 1234 is blocked. Nobody can pay with it."
- No codes: never show BLOCKED_PERM or an error code as the main text.

## Acceptance criteria
- Given the provider returns an error, When the app shows the result, Then the heading says the card is NOT blocked.
- Given no response within T s, When the timeout fires, Then the failure state appears with both actions.
- Given the user taps "Try again", When the request repeats, Then no duplicate block or order is created.
- Given two failed attempts, When the second error shows, Then "Call 24/7 block line" is the primary button.
- Given success, When the confirmation shows, Then it names the card's last 4 digits and contains no internal status code.

## Analytics
`card_block_started` · `card_block_succeeded{ms, attempt}` · `card_block_failed{reason, ms, attempt}` · `card_block_retry` · `hotline_call_tapped{after_attempt}`.

## Test cases
- Provider error → "NOT blocked" → retry → success.
- Timeout → failure state at T s, not a spinner forever.
- Network drops during the request → offline state; status re-checked on reconnect.
- Negative: double tap on "Try again" sends one request.
- Accessibility: failure heading announced as an alert by a screen reader.

## Do not break
- s5 relief "money is safe" stays the first thing after success.

## Owner decisions
- 24/7 block line number and whether it works without identification.
- Timeout T and the expected time N, after measuring block duration.

## Dependencies and effort
Provider error codes, idempotency key, telemetry. **M**: client states plus backend timeout and idempotency.
